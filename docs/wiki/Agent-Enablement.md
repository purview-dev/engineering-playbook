# Agent Enablement

## The rule

A repository tells an agent what it is, how it is laid out, and what its conventions are — in the
repository, in files an agent reads without being pointed at them.

Three files do the work:

| Path | What it is |
| -- | -- |
| `AGENTS.md` | The repository-wide source of truth for agents. Purpose, authority, layout, conventions, local commands, completion checklist. |
| `.github/copilot-instructions.md` | One job: defer to `AGENTS.md`. |
| `.agents/` | Agent content: skills, sub-agent definitions and prompts. Part-authored, part mirrored from the SDK. |

The rule has a corollary that is easy to miss: **nothing important may be discoverable only by reading the
code.** If the answer to "which of these two patterns is the intended one?" lives in the commit history or
in a colleague's head, the repository is not legible, and an agent will pick the wrong one at a rate that
looks like randomness.

## Why

A coding agent has the repository and nothing else. It has no colleague to ask, no institutional memory, no
sense of which of two plausible patterns the team settled on, and no way to tell a deliberate pattern from
an accident. It will confidently generalise from whatever it finds first.

This is not really an agent problem. Every failure mode above is also a new-joiner failure mode, and the
guidance that fixes it is the same guidance: state the purpose, draw the layout, name the conventions, and
write down the definition of done. The agent makes the cost visible sooner, because an agent does not ask.

## `AGENTS.md`

It should answer, in this order:

1. **Purpose and authority.** What the repository contains, that this file is the source of truth, that a
   more specific `AGENTS.md` in a subtree takes precedence, and what the agent must not do (operate outside
   the repository, read or commit secrets).
2. **Source of truth and layout.** A table of path → purpose. This is the single highest-value section: it
   is what stops an agent inventing a folder.
3. **Conventions.** The rules that are not derivable from the code — test naming, where domain content comes
   from, which project owns which concern.
4. **Local commands.** The `just` recipes, and what each is for.
5. **Completion checklist.** What "done" means: what to update, what to run, and what to state about the
   validation that ran.

Two properties matter more than completeness:

- **It is a table of contents, not an encyclopedia.** Long guidance belongs in the wiki, where it is
  published and reviewed; `AGENTS.md` points at it.
- **It is specific.** "Follow established patterns" is not guidance. "Domain content in a test comes from
  `TestBuilder`; never construct a domain type inline" is guidance.

`AGENTS.md` and the wiki cross-reference each other deliberately. A rule that only an agent is told is a
rule the humans have not written down, and a rule that only the wiki states is one the agent will not find.

## The `.agents/` folder

```text
.agents/
├── .gitignore          generated; lists the mirrored files
├── agents/             sub-agent definitions
├── prompts/            reusable prompts
└── skills/
    └── <skill-name>/
        ├── SKILL.md    the skill itself
        └── references/ optional deeper material the skill links to
```

A **skill** is a self-contained instruction set for one kind of task. It opens with YAML frontmatter whose
`description` is the trigger — it is what tells an agent that this skill applies:

```markdown
---
name: sdk-engineering-principles
description: "Use when creating or rationalising a repository that uses Purview.BuildSdk and you need the
  policy-level conventions for project placement, naming, namespace identity, test categories, and
  large-suite readability."
---
```

Writing a good trigger is most of writing a good skill. "Use when X, and you need Y" is far more useful
than a topic label, because the agent is matching a situation, not searching an index.

A **prompt** is a reusable instruction for a recurring task; an **agent** is a definition of a specialised
sub-agent with its own remit. Both are plain Markdown, and both are read the same way.

## The mirrored half

The SDK ships its own agent content and mirrors it into `.agents/` on build: skills for the SDK's own
conventions, prompts for diagnosing the agent folder itself, and sub-agent definitions for repository
rationalisation. You get the SDK's guidance without writing it.

The mirror is change-aware — unchanged files are never rewritten — and it writes a generated `.gitignore`
that lists exactly the files it owns:

```gitignore
# Generated by Purview.BuildSdk - do not edit.
#
# These files are mirrored into this folder from NuGet packages on build. Ignoring them
# keeps an SDK or package upgrade from showing up as local modifications. Files you
# author in this folder are not listed here and are tracked as normal.
/skills/sdk-engineering-principles/SKILL.md
...
```

That generated file is the whole design, and it is worth copying. It means:

- **An SDK upgrade is not a diff.** The mirrored files are ignored, so the working tree stays clean.
- **Your own content is tracked normally.** Anything you author is absent from the list and committed.
- **The boundary is explicit.** A file's presence in the list is a statement that the SDK owns it and an
  edit will be overwritten.

The SDK also keeps its state in `.purview/`, whose `.gitignore` is a single `*` — so the sync cache never
appears in a status output.

## How it is enforced

| Rule | Enforced by |
| -- | -- |
| The SDK's own guidance is present and current | The build (change-aware mirror into `.agents/`) |
| Mirrored content is not mistaken for local content | The build (generated `.agents/.gitignore`) |
| The SDK's cache never appears as a change | `.purview/.gitignore` |
| `AGENTS.md` exists, is accurate, and is specific | Review |
| `copilot-instructions.md` defers to `AGENTS.md` | Review |

## At your scale

- **Any repository.** Write `AGENTS.md`. It is the cheapest thing on this page and the one with the largest
  effect on an agent's first ten minutes.
- **A repository with conventions worth repeating.** Add a skill. The test is whether you have written the
  same explanation twice in review comments.
- **A repository with several task shapes.** Add a prompt per shape, and consider a sub-agent definition for
  the one that needs a different remit rather than more instructions.
- **A repository that others copy from.** Ship your skills in a package so the guidance travels with the
  code, in the same way the SDK does — the mirror mechanism is the pattern, not the SDK.
