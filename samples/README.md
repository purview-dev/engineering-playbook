# Acme persistence sample

This is the complete, runnable implementation of the two identifier conventions in the Engineering
Playbook:

1. **Well-known identifiers** — UUIDv5 over an installation-scoped namespace, for identities whose value
   is known before storage.
2. **Sequential GUID keys** — a provider-specific strategy applied to every GUID key by a model-finalising
   convention, for everything else.

The names and identifiers are the generic ones the playbook uses: `Acme`, `Installation`, `Customer`,
`Order`. Copy a file, replace the namespace, and the shape still holds.

The sample is deliberately outside `src/`. The reference implementation under `src/` is in-memory by
design and does not take a database dependency; this sample is where EF Core, the providers and the
complete wiring live. It is built and run by `just samples`, not by the canonical `just build`.

## Run it

```text
just samples
just samples --provider postgresql
just samples --provider uuidv7
just samples --print-constants
```

Without `just`:

```text
dotnet run --project samples/Acme.Persistence -- --provider sqlserver
```

The default store is EF Core's in-memory provider, so the sample runs with no database. The strategy is
still the real one: the generated values have the layout the named database sorts by.

Against a real store, pass a connection string:

```text
dotnet run --project samples/Acme.Persistence -- \
    --provider sqlserver \
    --connection "Server=(localdb)\mssqllocaldb;Database=AcmeSample;Trusted_Connection=True"

dotnet run --project samples/Acme.Persistence -- \
    --provider postgresql \
    --connection "Host=localhost;Database=acme_sample;Username=postgres;Password=postgres"
```

`uuidv7` is the portable fallback. It is genuinely sequential on PostgreSQL and not sequential on SQL
Server; the sample therefore refuses a connection string for it and keeps it on the in-memory store.

## What the run proves

The console does more than print values; it fails with a non-zero exit code if any check is untrue.

| Check | What it demonstrates |
| -- | -- |
| Identifier checks | RFC 4122 vectors, store-order monotonicity for all three strategies, the UUIDv7 trap, timestamp round-trips and range bounds. |
| Bootstrap twice | The second run creates no installation, tenant or principal. |
| Stable derived ids | The tenant and principal ids are identical on both runs. |
| Generated keys | A customer and an order receive keys from the configured strategy. |
| Value-object key | The order's `OrderId` receives an `OrderId`, not a raw `Guid`. |
| Foreign key excluded | The order's `CustomerId` is not generated by the convention. |
| Explicit configuration | The `Setting` key stays `ValueGeneratedNever`. |
| Indexed non-key column | The nullable indexed GUID is generated by the widened predicate. |
| Factory round-trip | The application-facing factory returns a value and its timestamp. |

## The catalogue and its ids

The default installation id is fixed so the derived values are reproducible. Change it with
`--installation <guid>` and every derived value changes, which is the isolation boundary working.

| Identity | Namespace | Name | Derived value |
| -- | -- | -- | -- |
| System tenant | `11111111-1111-4111-8111-111111111111` | `system-tenant` | `598f4dd5-4881-5833-8615-2915ab6f7ac9` |
| System principal | `11111111-1111-4111-8111-111111111111` | `system-service-principal` | `62331408-8c66-5cd0-82e1-d8fc91642fb4` |
| Seeded role | `11111111-1111-4111-8111-111111111111` | `role:admin` | `6809511c-6d6d-5d62-a381-3a631c4f7ec3` |

`--print-constants` prints exactly these values, ready to paste into a migration's `HasData` or
`InsertData` call. The migration cannot call `Uuid5.Create` itself; the test that guards the literal is
on the *Well-Known Identifiers* page.

## Migration constants

`--print-constants` is the helper for `HasData` and migration SQL, which cannot call `Uuid5.Create`
themselves. Paste the printed value into the migration:

```csharp
migrationBuilder.InsertData(
	table: "Tenants",
	columns: ["Id", "Name"],
	values: [Guid.Parse("598f4dd5-4881-5833-8615-2915ab6f7ac9"), "System"]);
```

And assert the literal in a test, so a namespace or name change cannot silently diverge:

```csharp
[Test]
public async Task SeededTenant_GivenTheMigrationConstant_MatchesTheDerivation()
{
	var namespaceId = Guid.Parse("11111111-1111-4111-8111-111111111111");
	var seeded = Guid.Parse("598f4dd5-4881-5833-8615-2915ab6f7ac9");

	await Assert.That(seeded).IsEqualTo(Uuid5.Create(namespaceId, "system-tenant"));
}
```

The sample has no migrations: the constants and the guard are documented here and on the *Well-Known
Identifiers* page, and the executable prints them, but applying them to a database is the adopting
repository's step.

## Copying it into a repository

1. Copy `Identifiers/Uuid5.cs` and `Identifiers/WellKnownIdentifiers.cs`.
2. Copy `Persistence/InstallationBootstrap.cs` and keep the read-or-insert sequence and the mismatch
   guard.
3. Copy `ValueGeneration/` and change the namespace.
4. Register the strategy where the provider is known:
   `options.UseSequentialGuids<SqlServerSequentialGuidProvider>()`.
5. Keep `ValueGeneratedNever()` on every derived key. The convention deliberately leaves it alone.
6. Copy the test shapes from the *Well-Known Identifiers* and *GUID Key Strategy* pages.
   `Verification/IdentifierVerification.cs` is their executable version: vectors, monotonicity,
   timestamp round-trip and range bounds.
7. In a single-provider application, make `AcmeDbContext` non-generic and hard-code the provider in
   `ConfigureConventions`, as the *GUID Key Strategy* page shows. The sample closes the context over
   the strategy so one executable can demonstrate all three.

## Notes

- `just pipeline-pr` builds, lints and tests `src/` only. Run `just samples` when you change the sample;
  that is its verification.
- The project has no analyzers because it sits outside `src/` and does not import the Purview SDK.
  CSharpier still formats it through `just lint-check`.
- `System.Security.Cryptography.Pkcs` is pinned to a patched 10.x version because the SQL Server
  provider's SQL client resolves a version with two published advisories. Remove the pin when the client
  ships a fixed dependency.
- The sample does not contain migrations. The derived constants and the migration guard are documented,
  not exercised against a database, so the sample can run anywhere.
